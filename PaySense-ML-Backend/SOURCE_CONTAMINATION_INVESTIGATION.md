# PaySense — Source Contamination Investigation

**Date:** 2026-08-27
**Trigger:** the 2026-08-26 audit found that the canonical test set inherits
the same ~35% "supplement"-source contamination `EDA_FEATURE_ENGINEERING.md`
had already documented in the training data, and that source-stratified
scoring shows the model's real organic-data performance (ROC-AUC 0.7465,
PR-AUC 0.1138, recall 2.55%) is far below every headline metric this
project has ever reported (ROC-AUC 0.8969, PR-AUC 0.5498, recall 39.53%).
This document is the follow-up forensic investigation into the mechanism,
whether it's fixable by retraining, and what the current measured
performance is under a clean evaluation protocol. Scripts:
`investigate_source_safe_retrain.py`,
`investigate_organic_only_threshold.py`. Neither touches any deployed
artifact — both are read-only investigations.

---

## 1. The mechanism, precisely (not "leakage" in the classic sense)

`EDA_FEATURE_ENGINEERING.md` §1.1 found `new_device_flag`/
`ip_location_mismatch` separate the supplement subset's label with zero
overlap. This investigation went further and checked every column in
`paysense_master_dataset.csv` for the same pattern. The result is more
severe than a two-column issue:

- **`device_risk_score` / `ip_risk_score`**: 100% null for all 20,000
  anchor rows, 100% populated for all 10,000 supplement rows. Fed into
  the model as ordinary numeric features (neither is in `DROP_COLS`), so
  the training pipeline's `SimpleImputer(strategy="median")` fills every
  anchor row with the *same constant* (the supplement-only median) —
  meaning these two columns are simultaneously (a) the exact formula the
  external source used to generate the supplement's fraud label, and (b)
  a near-perfect source-identity flag for the other two-thirds of the
  data, via the imputed-constant-vs-real-value distinction.
- **23 of ~30 numeric columns, and 12 of 14 categorical columns, are a
  single constant value across the entire 10,000-row supplement subset.**
  Confirmed directly: `day_of_week=0`, `is_weekend=0`,
  `failed_attempts_last_24h=0`, `transaction_velocity=0`,
  `recurring_payment_flag=0`, `usr_is_high_risk=0`,
  `balance_after_transaction=40398.73`, `usr_account_age_days=1291.0`,
  `usr_avg_txn_value_profile=544.55`, and 14 more — plus, categorically,
  `receiver_id="SYN_MRC_UNKNOWN"` (a literal synthetic marker),
  `usr_home_city="Mumbai"`, `usr_age_group="25-34"`,
  `payment_app="GPay"`, `device_type="Android"`, `mrc_size="Small"`, and
  6 more, all fixed across every one of the 10,000 rows.
- **This is not 10,000 diverse synthetic transactions — it is one
  templated synthetic profile, repeated 10,000 times**, with only
  `amount`, `hour_of_day`, `transaction_type` (2 values), and the two
  risk-score columns actually varying row to row.
- **A trivial single-column classifier
  (`device_risk_score.notnull()`) separates anchor from supplement with
  exactly 100.0000% accuracy** — verified directly, not estimated.

**Is this "leakage" in the classic train/test sense?** No — no row appears
in both splits, and `new_device_flag`/`ip_location_mismatch` are
legitimately available at prediction time for a real transaction. The
correct characterization is a **label-and-feature validity problem**: a
third of the dataset consists of rows whose label was generated by a
formula on two features the model also sees, wrapped in an otherwise
near-fully-constant, clearly-synthetic profile that makes that third
trivially identifiable and trivially solvable, independent of any genuine
fraud reasoning.

## 2. Does removing the contaminated rows fix organic performance?

**No — and this is the most important, most counterintuitive finding of
this investigation.** `investigate_source_safe_retrain.py` retrained
XGBoost with identical hyperparameters and monotonic constraints, on
anchor-only rows (16,087 train rows, 606 fraud), with `device_risk_score`/
`ip_risk_score` explicitly excluded, then evaluated on the exact same
held-out test partition used everywhere else in this project, sliced by
source:

| | Current model (blended training) | Source-safe model (anchor-only training) |
|---|---:|---:|
| Organic-only ROC-AUC | 0.7260 | **0.7261** |
| Organic-only PR-AUC | 0.0971 | **0.0993** |
| Organic-only recall @ τ=0.50 | 0.00% (0/157) | 0.00% (0/157) |
| Supplement-only ROC-AUC | 1.0000 | **1.0000** |

Organic-subset ROC-AUC/PR-AUC are statistically indistinguishable between
the two models. **Removing the contaminated training rows did not unlock
hidden organic-fraud-detection capability the contaminated data had been
suppressing — because it was never suppressing it.** XGBoost's tree
structure evidently solves the (trivially separable) supplement third
almost independently of how it handles the anchor two-thirds; the two
"live" in largely separate parts of the tree structure, so training on
one doesn't meaningfully cost or benefit the other.

**More strikingly: the source-safe model — which never saw a single
supplement row or the two risk-score columns during training — still
achieves a perfect 1.0000 ROC-AUC/PR-AUC on the supplement-only test
subset.** This means dropping two columns and 10,000 rows didn't stop the
model from perfectly ranking supplement fraud vs. legitimate — it simply
learned to do so from the *other* ~20 near-constant columns still present
(e.g. `amount`'s very different distribution by source is enough on its
own). **The takeaway: this is not a "two bad columns" problem fixable by
dropping two columns — it's a structural property of how dissimilar the
two sources are, and the only real fix is not mixing them, not patching
individual features.**

(A caveat on the raw-XGBoost recall numbers above: both show 0/157 at
τ=0.50 — this is raw XGBoost's contribution alone, not the full deployed
ensemble. Cross-referencing against the ensemble-level test in
`test_frozen_model_metrics.py`, which does show 4/157 organic TPs at the
same threshold, means those 4 true positives come entirely from the
rules/LightLR scorers, not XGBoost's own contribution.)

## 3. Current measured performance under a clean evaluation protocol

Every threshold ever selected in this project — including the 0.50
currently deployed — was tuned against a score distribution shaped
partly by the contaminated supplement data, and was selected on the same
partition its performance was then reported on (no separate validation
set). `investigate_organic_only_threshold.py` fixes both problems at
once: a proper 60/20/20 train/validation/test split, entirely on
anchor-only (organic) data, threshold selected on validation only, then
applied once to an untouched final test set.

```
Anchor-only pool:  20,000 rows, 763 fraud (3.815%)
Train:             12,000 rows (458 fraud)
Validation:         4,000 rows (153 fraud)
Test:               4,000 rows (152 fraud)

Validation ROC-AUC: 0.6506   PR-AUC: 0.0727
Validation sweep (0.05-0.95, step 0.05): NO threshold meets
  Recall>=75% AND Precision>=50% simultaneously (same conclusion as
  every prior sweep, now on clean data with correct methodology).
Frozen threshold (max-F1 fallback, selected on validation ONLY): 0.10

FINAL TEST (never touched during threshold selection):
  ROC-AUC=0.7050  PR-AUC=0.0945
  Precision=8.82%  Recall=21.05%  F1=0.1243
  TP=32  FP=331  FN=120  TN=3517
  Business constraint (Recall>=75% AND Precision>=50%): NOT satisfied
```

**21.05% recall at 8.82% precision is the current measured performance
under this clean evaluation protocol** — both historical figures (39.53%
blended, 2.55% at the old threshold on organic data alone) are documented
above because they're useful context, but neither is directly comparable
to this one: the blended figure is inflated by the contaminated
supplement subset, and the 2.55% figure used a threshold selected on a
different, contaminated score distribution rather than one calibrated
for this evaluation. Under the clean protocol, the model shows real,
non-trivial ranking skill on organic fraud (validation and test ROC-AUC
in the 0.65–0.70 range, PR-AUC roughly 2–2.5× the organic subset's own
base rate) — meaningfully above chance, but well short of the documented
Recall≥75% target at this measurement.

## 4. Conclusions and what this means for the deployed system

1. **The organic/supplement split is not a "two suspicious columns" bug —
   it's a wholesale data-quality problem affecting roughly a third of the
   dataset.** No amount of feature-dropping fixes it; the supplement
   source should be treated as unreliable for both training and
   evaluation going forward, not patched.
2. **Retraining on clean data alone does not materially improve organic
   ROC-AUC** — this was tested directly, not assumed (0.7260 before,
   0.7261 after). This does not mean better organic performance is
   impossible with different or additional data — only that removing the
   contaminated rows from the existing dataset, on its own, did not
   change the model's discrimination on organic data.
3. **The current model and available dataset do not meet the stated
   Recall≥75% requirement under the clean organic evaluation protocol.**
   This has now been checked three times with increasingly rigorous
   methodology (blended, anchor-only two-way split, and this proper
   train/validation/test split) and the result is consistent. This is a
   statement about the current model and current data, not a claim that
   Recall≥75% is unreachable for every possible future model or dataset.
4. **The deployed model and threshold are not changed by this
   investigation.** The deployed ensemble was never retrained on
   anchor-only data (that would require re-validating the rules/LightLR
   weights against a differently-distributed XGBoost score, a larger
   change than this investigation's scope). This document exists to give
   an honest account of what's actually going on, not to silently swap in
   a different model.
