# PaySense — Real EDA and Feature Engineering for OOD Generalization

**Date:** 2026-08-23
**Author's intent:** `GENERALIZATION_CHECK.md` and `SYNTHETIC_GROUNDING.md` diagnosed
that the frozen model ranks *worse* on an independently-generated,
full-40-feature synthetic dataset (ROC-AUC ~0.70) than on a real dataset
carrying only 15% of its features (ROC-AUC ~0.79-0.84 depending on model
variant). `OOD_GENERALIZATION_REMEDIATION.md` tried blending in more
synthetic data from a different generator seed — a genuine, evidence-backed
ranking improvement everywhere, but it never moved the deployed-threshold
recall (still 0/701 on real Dataset 1). Nobody had yet done real EDA on the
training data itself, or tried real feature engineering motivated by that
EDA. This document does both. Scripts: `eda_feature_engineering.py`
(feature engineering + retrain + evaluation). No retraining, fine-tuning, or
threshold recalibration touches `artefacts/paysense_model.pkl`,
`paysense_preprocessor.pkl`, or `paysense_threshold.pkl` anywhere in this
document.

---

## 1. EDA — what the data actually shows

### 1.1 The headline finding: a third of the model's training data has a
### near-tautological hard-flag-to-label relationship, and it is not organic

`paysense_master_dataset.csv` is built from two sources
(`paysense_pipeline.py`): a 20,000-row **anchor** (`transactions.csv`) and a
10,000-row **supplement**, schema-bridged from
`Financial Fraud Dataset/synthetic_fraud_dataset.csv`. The bridge
(`paysense_pipeline.py` lines 318-324) derives the supplement's
`new_device_flag`/`ip_location_mismatch` from that source's own
`device_risk_score`/`ip_risk_score` via a `> 0.70` threshold — but the
supplement's `is_fraud` label is **not** derived by this project's pipeline
at all; it is inherited as-is from the source file. Checking whether that
source's own label happens to line up with the same threshold reveals the
problem directly:

```
Supplement subset of paysense_master_dataset.csv (10,000 rows):
  new_device_flag=0      →  9,500 legit /     0 fraud
  new_device_flag=1      →      0 legit /   500 fraud
  ip_location_mismatch=0 →  9,500 legit /     0 fraud
  ip_location_mismatch=1 →      0 legit /   500 fraud
```

**Zero overlap, in both directions, for both flags.** Verified directly
against the raw source file (`Financial Fraud Dataset/synthetic_fraud_dataset.csv`,
`device_risk_score > 0.70` → 500/500 fraud, 9500/9500 legit) — this is not
an artifact introduced by this project's own schema bridge, it is baked
into the source dataset's own label-generation formula. This is **exactly**
the red flag `GENERALIZATION_CHECK.md` §2.2 used to reject a different
external dataset outright ("near-deterministic feature→label separation…
the signature of a label generated by a formula applied to those same
columns, not… an organically fraudulent population") — except this one is
sitting inside a third of the frozen model's own training data, and had not
been checked before now.

Contrast with the **anchor** subset (20,000 rows, a real transaction-style
dataset), where the same two flags are real but far weaker, organic signals:

| Feature | corr(`is_fraud`) — anchor | corr(`is_fraud`) — supplement |
|---|---:|---:|
| `new_device_flag` | 0.117 | **1.000** |
| `ip_location_mismatch` | 0.062 | **1.000** |
| `amount_deviation_score` | 0.029 | 0.000 (constant, std=0) |
| `transaction_velocity` | 0.097 | undefined (constant, std=0) |
| `failed_attempts_last_24h` | 0.042 | undefined (constant, std=0) |

The three behavioral features are **literally constant** across all 10,000
supplement rows (`amount_deviation_score`=0.444, `transaction_velocity`=0,
`failed_attempts_last_24h`=0 for every single row — they don't exist in the
source file and were filled with anchor-derived neutral values by the
schema bridge's Rule R4). So for a third of the model's training data, the
only usable fraud signal *at all* is the two hard flags, and those two
flags are literally the label in disguise.

**Quantifying how much of the model's training signal this touches:** in
the actual 24,000-row train partition (`random_state=42`, matching
`paysense_phase3.py` exactly), 7,913 rows (33.0%) are supplement-sourced,
and of the 1,010 real fraud rows in that partition, **404 (40.0%) are
supplement rows carrying this deterministic relationship.** SMOTE then
resamples the minority class ~23x to balance the training set — meaning a
large share of the *synthetic* minority points the model actually trains on
are interpolated from, or between, these 404 tautological fraud examples.

**This is a strong, concrete, previously-undocumented candidate root cause
for the OOD ranking gap.** It directly explains three things this project's
own documents already found but hadn't fully traced to a cause:

1. **Why `new_device_flag`/`ip_location_mismatch` are the model's most
   dominant SHAP features** (README.md, `RECALL_CEILING_REMEDIATION.md`) —
   not just because they're strong organic signals, but because a sizable
   slice of training data teaches the model they are *literally* the label.
2. **Why `RECALL_CEILING_REMEDIATION.md`'s 76 (see §1.2 below for today's
   recomputed count) invisible fraud rows are exactly the ones where both
   hard flags read clean** — they resemble the *anchor* distribution, where
   the flags are honest-but-weak, and the model (partly trained on the
   supplement's tautology) has learned to treat "flags clean" as a much
   stronger "not fraud" signal than the anchor data alone would justify.
3. **Why the model ranks *worse*, not better, on `SYNTHETIC_GROUNDING.md`'s
   independently-generated full-feature dataset** — that dataset deliberately
   built the flag→fraud relationship as a realistic ~4-5x elevation
   (14.69% vs 3.51% fraud rate by flag, §2.5 of that document), nothing like
   the training supplement's literal 100%/0% split. A model that over-trusts
   a near-deterministic flag relationship from training will systematically
   misrank any dataset — real or synthetic — that doesn't reproduce that
   same artifact, and Dataset 1's honestly-mapped 6/40 features don't even
   include the two flags at all, so it never triggers this failure mode the
   way a full-feature dataset does.

### 1.2 The 76-row (now 71-row) invisible-fraud diagnostic, extended

`RECALL_CEILING_REMEDIATION.md` found 76 of 253 canonical-test fraud rows
score below τ=0.05 even at the model's most aggressive swept threshold, and
showed their feature means. Recomputed today, directly against the
currently-deployed frozen artifacts (`artefacts/paysense_model.pkl`, the
monotonic-constraints model): **71 invisible / 182 caught at τ=0.05** — a
small drift from the 76/177 cited in that document, most likely because that
document's own number came from `recall_ceiling_remediation.py`'s
independent replica training rather than a load of the actual deployed
artifact; both numbers describe the same qualitative population. Going
beyond that document's feature-mean table:

**Interaction effect — how concentrated is "both flags clean" in each group:**

| Group | Both hard flags clean | Share |
|---|---:|---:|
| Invisible fraud (n=71) | 62 | **87.3%** |
| Caught fraud (n=182) | 49 | 26.9% |

Invisible fraud is overwhelmingly (87%) the "flags clean" population;
caught fraud is only 27% "flags clean" — a far sharper split than the raw
feature-mean comparison alone showed, and it is the direct empirical
signature of §1.1's finding: the model has learned "flags clean" as a very
strong exculpatory signal, and it is disproportionately wrong about it.

**Correlation structure — invisible vs. caught fraud rows:**

| Correlation | Invisible fraud | Caught fraud |
|---|---:|---:|
| `new_device_flag` ↔ `ip_location_mismatch` | −0.067 | **+0.595** |
| `new_device_flag` ↔ `transaction_velocity` | −0.186 | **−0.607** |

Caught fraud shows a strong internal structure — the two hard flags
co-occur (r=0.60) and trade off sharply against velocity (r=−0.61) — a
recognizable, learnable cluster. Invisible fraud shows almost no internal
correlation structure among these same features (all |r|<0.19) — it is a
diffuse, heterogeneous population, not a second clean cluster the model
simply never got a name for. This matters for what "fixing" it can
realistically achieve (see §3.3 and §4).

### 1.3 Distributional comparison — `paysense_master_dataset.csv` vs. real Dataset 1

Loaded side by side, all six honestly-shared fields
(`GENERALIZATION_CHECK.md` §3.1 mapping, reused verbatim):

| Field | Master dataset | Dataset 1 (real) | Test |
|---|---|---|---|
| `amount` | median ₹292.63, mean ₹643.95, skew 5.37 | median ₹12,676, mean ₹28,835.62, skew 1.05 | KS stat **0.668**, p<1e-300 — almost entirely different distributions, master's amounts run ~43x lower at the median |
| `hour_of_day` | near-uniform, std=6.52 | peaked (9.1% of mass at hour=12 alone), std=3.81 | KS stat **0.276**, p<1e-300 |
| `is_night_transaction` rate | 25.73% | 5.36% (derived) | Master over-represents night transactions by ~4.8x |
| `is_night_transaction` → fraud rate ratio (night/day) | 0.073/0.031 = **2.3x** | 0.115/0.0033 = **34.5x** | The *same* honestly-shared signal is a far weaker elevator in training data than in the real world |
| `device_type` mix | Android 76.9% / iOS 18.0% / Web 5.1% | Android 33.1% / iOS 33.4% / Web 33.5% | Master matches India's real device mix better; Dataset 1's near-perfectly-uniform device split is itself a minor realism caveat worth noting, not previously flagged |
| `txn_success_flag` corr(is_fraud) | **0.0036** (near-zero) | **−0.018** (FAILED 1.45x more fraud-prone than SUCCESS) | Success/failure carries almost no signal in training data but a real, if modest, one in the real world |
| `mrc_category` → fraud rate | Fuel highest (5.6%), fairly flat 4.0-5.6% across categories | Entertainment highest (1.03%), fairly flat 0.86-1.03% | Different top category, both flat — category alone is a weak signal in both, consistent |

**Reading these together:** the amount-scale and hour-shape mismatches are
real and measurable, but they don't explain the specific "synthetic
full-feature data ranks worse than sparse real data" puzzle — the model
still ranks Dataset 1 reasonably (ROC-AUC 0.77-0.84 across baseline/blended
variants) *despite* the amount/hour mismatch, because Dataset 1 doesn't
carry the two flags that drive §1.1's failure mode. The `is_night_transaction`
elevation-ratio gap (2.3x in training vs. 34.5x in the real world) and the
`txn_success_flag` near-zero-vs-real-signal gap are smaller in magnitude but
point the same direction as §1.1: **fields the model was trained to treat
as weak are, in the real world, sometimes much stronger — and fields it was
trained to treat as strong (the two hard flags) are, in a third of its own
training data, artificially, unrealistically strong.**

### 1.4 Feature correlations with `is_fraud` — training data vs. real Dataset 1

| Feature | corr — master (honest field) | corr — Dataset 1 (mapped) |
|---|---:|---:|
| `amount` | 0.122 | 0.168 |
| `hour_of_day` | −0.065 | −0.176 |
| `is_night_transaction` | 0.090 | 0.262 |
| `txn_success_flag` | 0.004 | −0.018 |

Every one of these correlations has the **same sign** in both datasets — a
genuinely reassuring finding, and evidence the model did learn some real,
transferable structure (consistent with `GENERALIZATION_CHECK.md`'s own
verdict). But three of the four are **meaningfully weaker in training data
than in the real world** (amount, hour, night-flag all 1.4x-3x stronger in
Dataset 1). None of these four honestly-shared fields shows the inverted
or spuriously-inflated pattern that would indict the model's basic logic —
the real problem, per §1.1, lives in the features Dataset 1 *doesn't*
carry, not in the ones it does.

## 2. Real external data — search results

### 2.1 Live download: not achievable in this environment

Tested early, per the task brief. `curl` reaches the open internet
(`kaggle.com` → HTTP 200, `raw.githubusercontent.com` → HTTP 301) and
`WebFetch` can retrieve static pages, but:
- Kaggle's dataset search/listing pages are JS-rendered — `WebFetch`
  (HTML→markdown, no JS execution) returns an empty shell with no dataset
  listings.
- Actually downloading a Kaggle dataset file requires either the `kaggle`
  CLI with an API token, or an authenticated browser session. Neither is
  present: no `kaggle` package installed, no `~/.kaggle/kaggle.json`, no
  `KAGGLE_*` environment variables.

**Honest conclusion: a genuinely new, live-downloaded dataset is not
achievable in this environment**, and no weak substitute (e.g. scraping an
unauthenticated preview) was forced in its place.

`E:\Projects\upi` already contains several UPI-fraud-labeled CSVs never
used by any of this project's three prior generalization documents. Both
were triaged with the exact same scrutiny `GENERALIZATION_CHECK.md` §2.2
applied (round fraud rates, near-deterministic separation, shared ID
backbones):

Also carries a `risk_score` column, the same kind of pre-computed leakage-shaped field GENERALIZATION_CHECK.md's Dataset 2 was rejected for. Not scored. |

### 2.3 Is Dataset 4 usable as additional *training* signal? No — stated plainly

Honest mapping to the frozen 40-feature schema yields **9/40 (22.5%)** —
better coverage than Dataset 1's 6/40, because `device_type`
(Android/iOS/Web — exact taxonomy match, no mapping needed),
`transaction_type` (P2P/P2M/Bill Payment/Recharge — direct subset match),
`day_of_week`, and `is_weekend` are all directly available:

```
amount, hour_of_day, day_of_week, is_weekend, device_type,
transaction_type, mrc_category, txn_success_flag, is_night_transaction (derived)
```

But **none of the personalization/behavioral features this model actually
depends on most** — `new_device_flag`, `ip_location_mismatch`,
`amount_deviation_score`, `transaction_velocity`,
`failed_attempts_last_24h`, any `usr_*`/`mrc_*` profile field — exist in
this dataset at all. A dataset that cannot supply the exact features §1.1
identified as the root of the problem cannot be used to teach the model a
better relationship for those features. **Verdict: not usable as additional
training signal for the problem this document is trying to fix — usable
only as a fifth held-out evaluation target**, and even there, at lower
value than Dataset 1 (it doesn't touch the flags that matter most either).
For completeness, a fast raw-XGBoost-only check (not the full per-row
ensemble path, given the time budget already spent on the three required
checks below) against the frozen model: ROC-AUC 0.7328, PR-AUC 0.0986,
0/5,008 caught at τ=0.30, max score 0.0193 — the same qualitative story as
Dataset 1 and Dataset 3, not scored further.

## 3. Feature engineering, motivated directly by §1

Two features were engineered and trained together in one variant (not swept
individually — a single ensemble evaluation against Dataset 1 alone costs
~18-20 minutes of real wall-clock time; sweeping 2-3 features individually
was not affordable within this task's time budget, and is flagged as a
follow-up rather than skipped silently).

### 3.1 `stealth_fraud_score` — a gated interaction term targeting §1.2's
### "flags clean" population, not a flat composite

```
stealth_fraud_score = (1 - new_device_flag) * (1 - ip_location_mismatch)
                       * mean(minmax(amount_deviation_score),
                              minmax(transaction_velocity),
                              minmax(failed_attempts_last_24h))
```

Min-max stats computed on **train-only** data (no leakage). This is
deliberately **not** `RECALL_CEILING_REMEDIATION.md`'s `composite_feature`
(a flat, ungated mean of the same three features) — that variant was
already tried and found to be the weakest of three (8/76 recovered, and the
only variant that made PR-AUC measurably worse). The gating term
`(1-flag)*(1-flag)` gives this feature a nonzero value *only* when both
hard flags read clean — i.e., exactly the region §1.2 showed contains 87.3%
of invisible fraud vs. 26.9% of caught fraud. Sanity-checked directly on
today's canonical test set before retraining anything: `stealth_fraud_score`
means 0.109 (invisible fraud) vs. 0.060 (caught fraud) vs. 0.066 (legit) —
invisible fraud rows score **nearly double** both other populations on this
feature, a real, targeted separation RECALL_CEILING's flat composite didn't
have reason to produce. Given `monotone_constraints=+1` (same treatment as
the three behavioral features it's built from — consistent design intent).

### 3.2 `hour_sin`, `hour_cos` — cyclical hour encoding

Motivated by §1.3: master's `hour_of_day` distribution (near-uniform,
std=6.52) differs materially from Dataset 1's real distribution (peaked,
std=3.81, KS stat=0.276) and forces XGBoost to treat the midnight
wrap-around (23→0) as two unrelated regions rather than adjacent. Cyclical
encoding removes that artificial discontinuity. No principled monotonic
direction, so `monotone_constraints=0` for both.

### 3.3 What this can and can't be expected to fix, stated before results

Per §1.2, invisible fraud is a diffuse population with weak internal
correlation structure, not a second clean cluster — `stealth_fraud_score`
gives the model a *chance* to use the (real but modest) behavioral
elevation this population shows, but §1.2's own numbers (behavioral means
elevated, not extreme, sitting inside the range plenty of legitimate
transactions also occupy — the same caveat `RECALL_CEILING_REMEDIATION.md`
§6 already raised) predict this is unlikely to be a large effect. This is
stated before the results below, not fitted to them afterward.

### 4.5 An unrelated but more important discovery, made while running this check

Computing the canonical test set's ensemble numbers (last row of §4.1)
required scoring through the real `src.fraud_model.score()` path rather
than raw `model.predict_proba()` — which every headline metric in
`README.md` and `paysense_report.tex` has used, tonight and before,
including the ones already re-verified multiple times. Doing that
revealed: **the real ensemble, on the model's own in-distribution test
set, behaves substantially differently from the raw-XGBoost numbers that
have been reported as "the deployed model's performance" all along.**

Confirmed directly for the actual currently-frozen model (not the
feature-engineered variant, to isolate this from §4.1-4.4's question):

| | Raw XGBoost only (what every doc reports) | Real ensemble (what `/predict` actually returns) |
|---|---:|---:|
| ROC-AUC | 0.8889 | 0.8969 |
| PR-AUC | 0.5352 | 0.5498 |
| Precision @ τ=0.30 | 86.44% | **40.81%** |
| Recall @ τ=0.30 | 40.32% | **51.78%** |
| TP / FP | 102 / 16 | 131 / 190 |

Precision more than halves and recall rises meaningfully. This is not a
bug in this check -- it's a real, structural consequence of how the
ensemble is built: the rules scorer contributes an always-on, unconditional
0.15 weight from a hand-tuned additive score (base 0.02, plus up to +0.35
for `new_device_flag`, +0.20 for `ip_location_mismatch`, +0.20 for a large
`amount_deviation_score`, etc.) that was never jointly calibrated against
the 0.30 threshold the way raw XGBoost's own score was in
`paysense_phase3.py`'s sweep -- so transactions XGBoost alone would
correctly score below 0.30 can still cross the deployed threshold once the
rules/LightLR contributions are blended in, and vice versa. **The deployed
threshold (0.30) was chosen by sweeping raw XGBoost's own score
distribution, not the real ensemble's** -- it may not be the right
operating point for the system that's actually deployed.

This means every "Key Results" precision/recall figure in this project
(66.14%/52.17%, then 98.98%/38.34%, then 86.44%/40.32% -- every version,
across every prior correction tonight) has been describing a component of
the deployed system, not the deployed system's own real behavior. That is
a separate, larger finding than anything else in this document and is
**not fixed here** -- flagged plainly for a deliberate follow-up decision,
the same way every other significant finding tonight was surfaced rather
than silently patched.

## 5. Verdict

**Feature engineering, as attempted here, is not a promising direction for
this specific gap.** Both engineered features are traceable to real EDA
findings (§1), but neither transfers: `stealth_fraud_score` is a NaN
no-op against Dataset 1 (which doesn't supply the columns it's built
from) and `hour_sin`/`hour_cos` alone isn't enough signal to move the
needle. The feature-engineered variant is worse than baseline on both
real-dataset checks (Dataset 1: ROC-AUC 0.79->0.76, PR-AUC 0.38->0.35;
Dataset 3: 0.60->0.57) and no better on the held-out synthetic set --
strictly dominated by the blended-training approach
(`OOD_GENERALIZATION_REMEDIATION.md`) on every axis tested. Between the
two levers tried across tonight's two OOD-improvement attempts, data
diversity (more/different training examples) clearly outperforms feature
engineering (new derived columns on the existing data) for this
particular generalization gap -- consistent with the underlying
diagnosis that the problem is the model's dependence on one generation
process's correlation structure, which more/different *data* addresses
more directly than new *features* computed from that same data.

Not deployed -- saved as `artefacts/paysense_model_feature_engineered.pkl`
/ `paysense_preprocessor_feature_engineered.pkl`, not wired into
`main.py`/`src/fraud_model.py`.

**The real-ensemble-vs-raw-XGBoost discrepancy (§4.5) is the more
important finding in this document and needs its own decision separately
from the feature-engineering question.**

## 6. Reproducing this check

```
cd PaySense-ML-Backend
venv\Scripts\python.exe eda_feature_engineering.py
```

Takes on the order of 30-40 minutes — one SMOTE + 400-tree XGBoost training,
then real-ensemble-path scoring (`src.fraud_model.score()`, one call per
row, the same per-request code path `/predict` uses) against the canonical
test set (6,000 rows), the held-out synthetic set (25,000 rows, several
minutes), real Dataset 1 (74,917 rows, ~18-20 minutes), and real Dataset 3
